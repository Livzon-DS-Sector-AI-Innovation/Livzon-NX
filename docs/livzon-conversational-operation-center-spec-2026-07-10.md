# Livzon 对话式智能运营中枢完整 Spec

> 文档状态：Draft for implementation  
> 版本：v1.1  
> 日期：2026-07-10  
> 适用范围：工厂管理平台、Livzon 助手、Hermes-Lite、平台调度器、飞书消息能力及各业务模块 Agent 工具  
> 核心约束：统一指标、数据口径、权限模型和判定规则由平台预设；管理员可在权限管理中为用户分配模块访问权限，系统将有效授权同步为该用户的 Livzon 助手访问范围；任务、自动化、监测、推送、查询、追溯和处置均通过 Livzon 对话完成。

版本更新：v1.1 增加管理员用户模块授权、Livzon 有效访问范围同步、授权版本校验、管理 API、审计和验收要求。

## 1. 文档目的

本 Spec 用于建立 Livzon 助手后续演进的统一基础，使其从当前的对话与工具调用入口，升级为可持续扩展的“对话式智能运营中枢”。

本期重点解决：

1. 明确普通用户与管理员可查看内容的边界。
2. 支持管理员为用户分配模块访问权限，并可靠同步用户的 Livzon 助手访问范围。
3. 支持在对话中创建、修改、启停、运行和查看自动化任务及定时任务。
4. 支持在对话中查看推送记录、执行日志、步骤结果和审计信息。
5. 兼容平台中相互独立的模块，以及存在数据联调、事件联动和任务编排的模块。
6. 建立稳定的能力注册、流程定义、执行、观测和版本兼容基础，降低后续模块接入成本。

## 2. 产品定位

Livzon 助手定位为：**对话驱动的平台智能运营中枢**。

它不是单纯的问答机器人，也不是一个允许大模型自由操作系统的超级管理员。它承担以下四类职责：

- **理解入口**：把用户的业务语言转换为结构化查询、监测规则、定时计划和自动化流程。
- **调度入口**：通过平台已注册的能力执行查询、检测、任务编排和消息推送。
- **运行解释器**：解释任务为何触发、执行到哪一步、为何失败、消息发给了谁。
- **治理窗口**：在固定权限模型和管理员授权结果下，为用户提供个人范围视图，为管理员提供权限分配、平台运行、审计和诊断视图。

### 2.1 核心设计结论

大模型只负责“理解与编译”，不负责长期调度和不受控执行：

```mermaid
flowchart LR
    U["用户自然语言"] --> P["意图解析与计划编译"]
    P --> V["Schema、能力、权限与风险校验"]
    V --> C["可读预览与用户确认"]
    C --> D["持久化自动化定义"]
    D --> S["确定性调度与事件触发"]
    S --> E["工具网关与流程执行器"]
    E --> O["日志、推送、审计与闭环"]
```

对话文本不是运行时事实来源。每个被启用的自动化都必须编译为经过校验、可版本化、可审计的结构化定义。

## 3. 已有基础与差距

### 3.1 可复用基础

当前代码已经具备以下基础：

- `AgentSession`、`AgentMessage`：对话会话和消息记录。
- `AgentToolCall`、`AgentConfirmation`：工具调用记录和写操作确认。
- `AgentWorkflow`、`AgentWorkflowRun`：用户工作流和运行状态。
- `ToolRegistry`、`ToolExecutor`：工具注册、参数校验、权限检查、确认和审计入口。
- `workflow_allowed`、`human_decision_required`、`risk_level`：工作流准入和风险元数据。
- 平台 `SchedulerEngine`：支持 cron、interval、fixed-time 三类策略，以及静态任务和动态任务生成器。
- `audit.logs`：平台审计基础表。
- 飞书组织同步、用户映射、消息发送、交互卡片及卡片动作记录。
- 模块注册表和跨模块 `public_api.py` 约束。

### 3.2 当前主要差距

- 当前工作流偏向“顺序工具步骤”，缺少定时、事件、条件、等待、分支、重试和补偿语义。
- 调度器的最近执行状态主要保存在进程内存，不适合作为用户可管理自动化的唯一运行基础。
- 当前用户权限主要依赖单一 `role` 字段，缺少用户—模块授权、授权版本及 Livzon 有效访问范围同步机制。
- 工作流归属以 `user_id` 为主，尚未形成个人范围、部门范围、平台范围和管理员视图的统一规则。
- 缺少独立的自动化版本、触发器、步骤运行、推送投递和运行事件模型。
- 缺少用户与管理员差异化的日志输出、字段脱敏和业务数据二次授权检查。
- 当前 Agent API 主要覆盖聊天、工具、技能和确认；工作流的查询、运行信息多数通过内部工具完成，尚未形成完整的可观测查询契约。
- 飞书已具备发送能力，但缺少统一的投递记录、幂等键、重试、聚合降噪和送达闭环模型。

## 4. 范围与非目标

### 4.1 本 Spec 范围

- 对话式自动化和定时任务管理。
- 普通用户与管理员的可见性区分。
- 管理员用户模块授权、Livzon 访问范围同步及同步状态审计。
- 独立模块、可观测模块和可编排模块的统一接入契约。
- 自动化定义、版本、触发、执行、推送和审计模型。
- 飞书精准推送、交互回写和投递追踪。
- 面向后续扩展的兼容策略、实施阶段、测试与验收标准。

### 4.2 非目标

- 不允许通过对话或 Agent 工具创建、修改或提升权限；用户模块权限只能由具备权限管理资格的管理员在平台权限管理功能中设置。
- 不允许管理员修改平台内置的权限判定规则、指标口径和数据治理规则；管理员管理的是用户授权关系，不是安全策略代码。
- 不将模块化单体改造成微服务。
- 不允许 Agent 直接访问数据库、任意后端 API 或第三方系统。
- 不允许自动化代替人工完成审批、驳回、批准、责任认定和关键系统重启。
- 本期不建设复杂的拖拽式流程设计器；结构化卡片仅用于对话中的预览、查看和确认。

## 5. 产品原则

1. **权限先于意图**：助手理解了用户意图，不代表用户有权查看或执行；管理员授权也必须经过平台固定策略判定。
2. **创建时校验，运行时复验**：自动化创建时检查权限，每次触发前再次检查，防止人员调岗或权限撤销后继续执行。
3. **元数据与业务内容分离**：平台管理员可以治理任务，但不因管理员身份天然获得全部业务明细。
4. **模块自治**：业务规则保留在模块 Service；编排层只依赖注册能力、公开契约和事件。
5. **确定性执行**：调度、条件判断、重试、幂等和超时由代码执行，不由大模型临场决定。
6. **全过程可追踪**：一次对话创建的自动化，从确认、版本、运行、工具调用到飞书投递均可关联。
7. **默认安全**：写操作默认确认；高风险人工决策不进入无人值守工作流。
8. **渐进接入**：模块可以只提供查询能力，也可以逐步增加事件和可编排动作，无需一次完成全部改造。
9. **授权单一事实源**：用户模块授权以身份与权限服务为唯一事实来源，Livzon 保存的访问范围只能是可失效、可重建的派生快照。

## 6. 用户与管理员可查看权限

### 6.1 两层视图与底层规则

首期产品体验区分为“普通用户视图”和“管理员视图”。底层使用平台预设的角色、模块权限项、数据范围和敏感字段规则。具备 `permission_admin` 管理资格的管理员可以在平台权限管理功能中为用户分配模块授权；权限配置能力不开放给 Livzon 对话、Hermes-Lite 或普通 Agent 工具。

管理员分为平台治理身份和业务数据身份：

- **平台管理员能力**：查看全平台任务元数据、运行健康、失败原因、投递状态和脱敏审计，执行暂停、隔离、重试等治理动作。
- **业务数据访问能力**：查看具体订单、质量、人员等业务内容，仍必须满足对应模块的数据权限。

因此，“管理员可看到任务存在和失败”不等于“管理员可看到任务处理的全部业务数据”。

### 6.2 用户模块授权与 Livzon 范围同步

管理员按用户分配模块授权。首期每个模块至少支持以下固定权限项，后续可以在不改变同步协议的情况下增加细粒度权限：

- `module.view`：进入模块并查看授权数据范围内的信息。
- `module.agent.read`：允许 Livzon 调用该模块的只读工具。
- `module.agent.execute`：允许用户确认后调用该模块的受控写工具。
- `module.agent.automate`：允许该用户把模块能力放入定时任务或自动化流程。
- `module.admin`：模块治理能力，仅可由具备相应授权资格的管理员授予。

用户的 Livzon 有效访问范围按交集计算：

```text
有效范围 = 用户当前模块授权
         ∩ 工具 permission_key / required_roles
         ∩ 用户在模块内的数据范围
         ∩ 工具风险与 workflow_allowed 策略
         ∩ 当前账户和模块启用状态
```

同步要求：

1. 管理员保存用户模块授权后，身份与权限服务提交新 `grant_version`。
2. 同一事务写入权限变更和同步 Outbox 事件，事件类型为 `identity.user_module_grants.changed.v1`。
3. Livzon 权限同步器消费事件，重新解析该用户可见模块、可调用工具和可编排工具，生成新的 `agent_scope_version` 派生快照。
4. 同步成功后记录来源授权版本、同步时间、能力注册表版本和摘要；同步失败进入重试队列并向管理员显示失败原因。
5. 管理员可以手动触发“重新同步 Livzon 范围”，但不能手工编辑派生快照。
6. 每次对话、工具调用和自动化运行仍查询当前授权版本；发现快照版本落后时必须实时重建或拒绝执行，禁止使用过期范围放行。

管理员不能授予自己无权管理的模块或数据范围。涉及批量授权、模块管理员授权和权限扩大时必须二次确认并写入审计。

用户可以在对话中询问“我可以访问哪些模块”“为什么不能查询质量数据”，助手只读返回当前有效范围、缺失权限项和申请路径，不能代用户申请通过或修改权限。

### 6.3 查看权限矩阵

| 信息类型 | 普通用户 | 管理员 |
|---|---|---|
| 自己的模块权限和 Livzon 有效范围 | 可查看，不可修改 | 可查看；具备授权资格时可修改模块授权并同步 |
| 他人的模块权限 | 不可查看 | 仅可查看和管理自己有权授权的模块与数据范围 |
| 权限规则、权限项定义 | 不可修改 | 不可通过业务管理功能修改平台内置规则 |
| 自己创建的自动化/定时任务 | 可查看完整定义和状态 | 可查看 |
| 他人私人任务 | 不可查看 | 可查看元数据；业务内容按模块权限脱敏 |
| 部门共享任务 | 在部门及模块权限范围内可查看 | 可查看元数据与治理状态 |
| 平台系统任务 | 仅查看与自己有关的结果摘要 | 可查看注册、状态、健康与执行历史 |
| 自己发起的运行 | 可查看允许的数据、步骤摘要和错误建议 | 可查看 |
| 他人运行 | 默认不可查看；共享任务按范围查看摘要 | 可查看运行元数据，业务载荷按权限过滤 |
| 发给自己的飞书消息 | 可查看内容、状态和关联任务 | 可查看 |
| 发给他人的飞书消息 | 不可查看内容与身份 | 可查看投递元数据；消息内容按业务权限脱敏 |
| 自己的操作审计 | 可查看面向用户的操作时间线 | 可查看完整脱敏审计 |
| 平台策略拒绝、权限拒绝 | 仅查看自己的拒绝原因 | 可查看全平台统计与脱敏明细 |
| Secret、Token、密码、密钥 | 永不可查看 | 永不可查看明文 |

### 6.4 服务端强制规则

所有查看操作必须由服务端根据当前用户计算范围，不能信任 LLM 生成的 `user_id`、`view_scope` 或过滤条件。

每次查询至少执行：

1. 身份确认：当前登录用户和会话归属一致。
2. 授权版本确认：用户当前 `grant_version` 与 Livzon 快照的 `source_grant_version` 一致，或已完成实时重建。
3. 对象范围判断：本人、共享范围、部门范围或管理员治理范围。
4. 模块权限判断：是否具备目标模块对应的 `view/read/execute/automate` 权限项。
5. 数据范围判断：是否有权访问目标部门、工厂、产品、批次等数据。
6. 字段级过滤：对敏感输入、输出、收件人和异常堆栈进行脱敏。
7. 返回审计：管理员查看敏感治理信息或修改用户授权时写入审计。

### 6.5 权限变化后的行为

- 自动化定义保存创建时的 `policy_snapshot`，用于解释当时为何允许创建。
- 每次运行前使用当前权限重新判定，不使用历史快照代替当前权限。
- 管理员扩大用户模块权限后，新范围只有在授权事务成功且 Livzon 同步完成或实时校验通过后生效。
- 管理员收回 `module.agent.automate` 时，涉及该模块的自动化立即进入 `suspended_policy`；只收回 `module.agent.execute` 时，相应写步骤不可继续执行。
- 所有者权限不足时，自动化进入 `suspended_policy`，不继续执行并通知所有者。
- 所有者离职或停用时，个人任务暂停；管理员可在审计后转交所有权。
- 用户失去业务数据权限后，历史运行中的业务载荷立即按当前权限隐藏，但仍可查看本人操作的非敏感元数据。

## 7. 对话式交互需求

### 7.1 支持的意图

| 意图 | 示例 |
|---|---|
| 创建定时任务 | “每个工作日 9 点检查昨日质量异常，发给我。” |
| 创建监测任务 | “库存低于安全库存时提醒对应仓库负责人。” |
| 创建跨模块自动化 | “采购到货后检查入库状态，未入库两小时后提醒采购和仓储。” |
| 查看任务 | “我有哪些正在运行的自动化？” |
| 查看定时计划 | “下周有哪些任务会执行？” |
| 修改任务 | “把刚才的日报改到 8:30，并跳过法定节假日。” |
| 启停/删除/复制 | “暂停华东区预警；复制给华南区；删除测试任务。” |
| 查看运行 | “昨晚那个流程执行到哪一步了？” |
| 查看失败 | “为什么今天没有发晨报？” |
| 查看推送 | “今天发给我的飞书消息有哪些？” |
| 查看审计 | “谁在什么时候修改了这个任务？” |
| 管理员治理 | “列出过去 24 小时失败率最高的任务并给出原因。” |

### 7.2 创建对话流程

助手必须按以下顺序处理：

1. 识别目标、业务对象、范围、触发方式、动作、接收人和结束条件。
2. 查询能力注册表，确认涉及模块已经暴露所需能力。
3. 对缺失且不可安全推断的关键字段进行澄清。
4. 生成结构化草案并执行权限、风险、Schema、时间和收件人预检查。
5. 如果是数据监测，允许以历史数据执行模拟，返回预计触发次数和消息量。
6. 在对话中显示可读预览，包括影响范围、频率、收件人、风险和预计成本。
7. 用户确认后持久化版本并启用；写入审计和来源会话。

### 7.3 修改语义

- 每次修改创建新版本，不原地覆盖已运行版本。
- 未明确指定对象时，助手应使用当前对话最近引用的唯一任务；存在歧义时要求用户选择。
- 修改定时、范围、动作、接收人或业务条件后必须重新校验权限。
- 影响范围扩大、消息量明显增加或引入新写操作时必须再次确认。
- 已开始的运行继续使用启动时快照；新版本只影响后续运行。

### 7.4 对话中的结构化展示

不建设独立任务配置页面。助手在对话中返回可交互的结构化信息：

- 任务列表卡：名称、类型、状态、所有者、范围、下次执行时间、最近结果。
- 任务详情卡：触发器、条件、步骤、收件人、版本、权限状态。
- 运行时间线：触发、各步骤、重试、推送、结束状态。
- 推送记录表：接收范围、渠道、状态、尝试次数、关联运行。
- 审计差异卡：修改人、修改时间、修改前后字段差异、原因。
- 管理员健康摘要：成功率、失败率、积压量、重复推送、策略暂停任务。

卡片按钮只是对话指令的快捷入口，例如“查看详情”“暂停”“重试”“解释失败”；所有写操作仍走统一确认链路。

## 8. 自动化领域模型

### 8.1 概念分离

为避免把定时任务、工作流和推送混为一个大对象，采用以下概念：

- **WorkflowDefinition**：做什么，包含步骤和数据映射。
- **Automation**：谁拥有、作用范围是什么、使用哪个工作流、当前是否启用。
- **Trigger**：何时启动，包括手动、定时、数据事件和平台事件。
- **AutomationVersion**：某次确认后不可变的完整定义快照。
- **AutomationRun**：一次实际运行。
- **StepRun**：一次运行中的单个步骤记录。
- **PushDelivery**：一次面向一个接收目标的消息投递记录。
- **RunEvent**：状态变化、重试、等待、取消、人工动作等时间线事件。

### 8.2 建议数据表

保持现有 `core.agent_workflows` 和 `core.agent_workflow_runs` 可迁移，不另建微服务。建议逐步补充：

| 表 | 用途 | 关键字段 |
|---|---|---|
| `identity.user_module_grants` | 用户模块授权事实源 | `user_id`、`module_code`、`permissions`、`data_scope`、`grant_version`、`granted_by`、`status` |
| `core.agent_access_scope_snapshots` | Livzon 有效范围派生快照 | `user_id`、`source_grant_version`、`agent_scope_version`、`modules`、`tool_names`、`workflow_tool_names`、`registry_version`、`sync_status` |
| `core.agent_automations` | 自动化主对象 | `owner_user_id`、`scope_type`、`scope_ref`、`status`、`active_version_id`、`source_session_id` |
| `core.agent_automation_versions` | 不可变版本 | `version`、`definition`、`policy_snapshot`、`capability_versions`、`created_by`、`change_summary` |
| `core.agent_automation_triggers` | 触发配置 | `trigger_type`、`schedule`、`event_type`、`filter`、`timezone`、`next_fire_at` |
| `core.agent_automation_runs` | 运行实例 | `trigger_id`、`version_id`、`status`、`started_at`、`finished_at`、`correlation_id`、`error_code` |
| `core.agent_step_runs` | 步骤执行记录 | `run_id`、`step_key`、`operation`、`attempt`、`status`、`input_summary`、`output_summary` |
| `core.agent_run_events` | 运行时间线 | `run_id`、`event_type`、`actor_type`、`actor_id`、`payload_summary`、`occurred_at` |
| `core.agent_push_deliveries` | 推送投递 | `run_id`、`channel`、`recipient_type`、`recipient_ref`、`status`、`external_message_id`、`idempotency_key` |

说明：

- 表之间按项目规范不建立数据库外键，通过 UUID 和索引保持逻辑关联。
- `identity.user_module_grants` 是授权事实源；`agent_access_scope_snapshots` 仅用于加速和解释，允许失效和重建，不能反向覆盖授权事实。
- 同一用户的授权变更使用单调递增 `grant_version`；快照必须记录对应来源版本，便于发现同步滞后。
- JSONB 只保存版本快照、条件树和数据映射；核心筛选字段必须独立列并建立索引。
- 原始大响应不写入运行表和审计表，只保留摘要、对象引用或受控存储引用。
- `AgentWorkflow` 可先作为 `WorkflowDefinition` 的兼容来源，逐步迁移到 Automation + Version 模型。

### 8.3 状态定义

自动化状态：

- `draft`：已编译但未确认。
- `enabled`：允许触发。
- `paused`：用户或管理员主动暂停。
- `suspended_policy`：权限或策略变化导致暂停。
- `quarantined`：连续失败、重复推送或异常行为被平台隔离。
- `archived`：归档，不再执行。

运行状态：

- `queued`、`running`、`waiting`、`succeeded`、`partially_succeeded`、`failed`、`cancelled`、`skipped_policy`、`expired`。

投递状态：

- `pending`、`sending`、`sent`、`delivered`、`interacted`、`failed`、`suppressed`、`expired`。

## 9. 工作流定义协议

### 9.1 v1 节点类型

首期支持：

- `tool`：调用已注册 Agent 工具。
- `condition`：基于结构化字段执行确定性条件判断。
- `transform`：字段选择、映射、聚合和模板渲染。
- `notify`：生成并投递飞书消息。
- `wait`：等待固定时长或等待到指定时间。
- `end`：以成功、部分成功或跳过状态结束。

后续兼容：

- `event_wait`：等待业务事件。
- `parallel`、`join`：并行分支与汇合。
- `human_task`：创建人工待办并等待处理结果，不代表 Agent 代替人工决策。
- `subflow`：引用已发布的可复用子流程。

### 9.2 定义示例

```json
{
  "schema_version": "1.0",
  "name": "采购到货未入库提醒",
  "steps": [
    {
      "key": "get_arrivals",
      "type": "tool",
      "operation": "procurement.list_arrivals",
      "input": {"status": "arrived"}
    },
    {
      "key": "check_receipt",
      "type": "tool",
      "operation": "warehouse.list_receipts",
      "input": {"arrival_ids": "${steps.get_arrivals.output.ids}"}
    },
    {
      "key": "has_delay",
      "type": "condition",
      "expression": {"field": "steps.check_receipt.output.overdue_count", "op": "gt", "value": 0}
    },
    {
      "key": "notify_owners",
      "type": "notify",
      "template": "arrival_not_received_v1",
      "recipients": [{"type": "business_owner", "source": "steps.get_arrivals.output.owner_ids"}]
    }
  ]
}
```

禁止在定义中保存任意 Python、SQL、JavaScript、Shell 或未经白名单的表达式。条件和数据映射必须使用受限 DSL，并通过 Pydantic Schema 校验。

## 10. 模块接入与深度融合

### 10.1 模块接入等级

模块可按自身成熟度逐步接入：

| 等级 | 能力 | 适用场景 |
|---|---|---|
| L0 独立模块 | 不接入 Agent，仅保留原页面和 API | 尚未准备接入的模块 |
| L1 可查询 | 注册只读工具 | 对话查询、汇总、解释 |
| L2 可执行 | 注册受控写工具 | 用户确认后的业务写操作 |
| L3 可编排 | 工具声明 `workflow_allowed=true`，支持幂等与结构化输出 | 定时任务、跨模块工作流 |
| L4 可事件联动 | 发布版本化业务事件并支持关联查询 | 实时监测、闭环自动化 |

独立模块无需为了 Livzon 改变内部结构；只有进入 L1 以上时才提供明确的 Agent 能力契约。

### 10.2 能力清单扩展

在现有 `AgentToolSpec` 基础上，以向后兼容方式增加可选元数据：

- `capability_version`：能力契约版本。
- `module`：所属模块。
- `permission_key`：平台固定权限键。
- `data_scope_type`：数据范围类型。
- `sensitivity`：输出敏感等级。
- `idempotent`：是否支持安全重试。
- `supports_dry_run`：是否支持模拟。
- `timeout_seconds`：建议超时。
- `output_schema`：稳定的结构化输出契约。
- `events_emitted`：成功后发布的业务事件。
- `deprecated_at`、`replacement_operation`：弃用兼容信息。

未提供新字段的现有工具继续按当前规则工作，但不能自动获得事件编排、高级重试等能力。

### 10.3 独立模块规则

- 工具 handler 仅调用本模块 Service。
- 飞书业务配置和业务流程仍归所属模块管理。
- 模块只需注册自己的只读或写入能力，不需要理解其他模块。
- Livzon 可以查询该模块，但不能自动建立跨模块数据映射。

### 10.4 跨模块编排规则

- 编排器只按注册 operation 调用工具，不导入模块内部 Service 或 Repository。
- 模块之间的直接业务协作优先通过目标模块 `public_api.py`。
- 跨模块数据传递使用稳定业务标识，例如 `product_id`、`batch_id`、`purchase_order_id`，不传递 ORM 对象。
- 每个步骤输出必须提供清晰的业务引用和可供后续步骤使用的结构化字段。
- 跨模块流程发布前检查全部能力版本、字段映射和权限交集。
- 任一模块能力弃用时，平台扫描受影响自动化并通知所有者迁移。

### 10.5 事件契约

事件名称采用 `<module>.<resource>.<verb>.v<major>`，例如：

- `procurement.arrival.confirmed.v1`
- `warehouse.receipt.completed.v1`
- `quality.deviation.created.v1`

事件信封至少包含：

```json
{
  "event_id": "uuid",
  "event_type": "warehouse.receipt.completed.v1",
  "occurred_at": "2026-07-10T09:00:00+08:00",
  "producer": "warehouse",
  "subject": {"type": "receipt", "id": "uuid"},
  "actor": {"type": "user", "id": "uuid"},
  "correlation_id": "uuid",
  "data": {}
}
```

事件只携带触发所需最小数据；执行器需要详情时再通过目标模块工具查询并重新执行权限判断。

## 11. 调度与执行架构

### 11.1 调度器演进

保留现有 `SchedulerEngine`、`SchedulerRegistry`、`TaskDefinition` 和 `TaskGenerator`：

- 代码定义的系统任务继续使用 `TaskDefinition`。
- 模块内数据库驱动任务继续使用 `TaskGenerator`。
- 新增一个平台级 `AgentAutomationGenerator`，扫描持久化触发器的 `next_fire_at`，创建运行实例并交给工作流执行器。

这样无需将调度器替换为新框架，也不会让每个自动化注册成进程内静态任务。

### 11.2 可靠性要求

- 触发器领取使用数据库原子更新或 `FOR UPDATE SKIP LOCKED`，避免多实例重复触发。
- 每次触发生成稳定 `idempotency_key`，相同自动化、版本和触发窗口只能创建一个运行。
- `next_fire_at` 持久化，服务重启后可恢复。
- 支持错过触发策略：`skip`、`run_once`；首期默认 `run_once`，但最多补执行一次。
- 单步骤根据能力的幂等声明决定是否自动重试。
- 默认重试使用指数退避并带随机抖动；非幂等写操作不自动重试。
- 每个自动化设置并发策略：`forbid`、`queue_one`、`allow`；首期默认 `forbid`。
- 连续失败达到阈值后进入 `quarantined`，停止继续制造告警和重复消息。
- 所有运行使用版本快照，不能读取执行期间被修改的新定义。

### 11.3 执行身份

无人值守任务不能使用匿名系统身份绕过权限。每次运行同时记录：

- `service_actor`：执行任务的平台服务身份。
- `acting_user_id`：自动化所有者或被明确授权的责任主体。
- `trigger_actor`：触发者，可能是用户、系统时间或业务事件。

工具执行时以 `acting_user_id` 重新检查权限；审计中同时记录服务执行和责任主体。

## 12. 飞书推送与闭环

### 12.1 收件人解析

对话允许使用“我、负责人、部门负责人、指定用户”等业务表达，但保存时必须编译为结构化收件人规则：

- `user`：固定本地用户 ID。
- `owner_field`：从业务对象责任人字段解析。
- `department_leader`：按部门解析负责人。
- `role_in_scope`：在固定业务范围内解析角色。

运行时从本地身份映射解析 `feishu_open_id`。不要在自动化定义中长期保存明文外部身份列表，以免组织变化后继续误发。

### 12.2 投递记录

每个最终接收目标创建一条 `PushDelivery`，至少记录：

- 关联自动化、运行和步骤。
- 渠道、模板版本、接收目标类型和本地引用。
- 飞书外部消息 ID。
- 发送状态、尝试次数、最近错误码和时间。
- 去重键、聚合键、交互动作状态。

普通用户查看自己的消息内容和状态；管理员查看全局投递健康与脱敏内容。

### 12.3 降噪与幂等

- 相同 `idempotency_key` 不重复发送。
- 支持同类异常在时间窗口内聚合。
- 支持静默期、工作时间和摘要模式。
- 恢复通知与异常通知使用同一 `incident_key` 形成闭环。
- 消息模板和变量分离，模板版本进入运行快照。
- 飞书发送成功但本地超时时，通过外部消息 ID或业务幂等键进行对账，不直接重复发送。

### 12.4 交互卡片

卡片动作可提供：查看详情、确认收到、标记处理中、创建待办、忽略本次、暂停任务。

卡片点击回调必须：

1. 校验签名、动作是否过期和点击人身份。
2. 重新执行权限判断。
3. 写入 `RunEvent` 和审计。
4. 只调用已注册工具；需要责任判断的动作跳转业务页面由人工处理。

## 13. 可观测性、日志与审计

### 13.1 统一关联标识

一次业务链路使用以下标识串联：

`session_id → automation_id → version_id → trigger_id → run_id → step_run_id → tool_call_id → push_delivery_id → audit_id`

同时生成一个贯穿链路的 `correlation_id`，用于对话查询和管理员诊断。

### 13.2 三层信息模型

- **用户时间线**：业务可读描述，例如“09:00 开始检查，发现 3 条异常，向你发送 1 条消息”。
- **运行日志**：步骤状态、耗时、重试、错误码、输入输出摘要，供有权限用户和管理员排查。
- **审计日志**：谁在何时以什么身份查看、创建、修改、确认、触发或治理了什么对象，记录不可抵赖的前后差异。

不要把技术堆栈、Token、Secret、完整提示词、完整第三方响应和敏感业务载荷直接展示给普通用户。

### 13.3 管理员治理查询

管理员可通过对话查询：

- 全平台启用、暂停、隔离和策略挂起任务数量。
- 按模块、所有者、时间范围统计成功率、延迟和失败类型。
- 长时间运行、重复触发、重复推送和无人处理异常。
- 能力版本升级影响的自动化。
- 权限撤销后被自动暂停的任务。
- 飞书投递失败、身份映射缺失和交互回调异常。

管理员治理动作包括：暂停、隔离、重试幂等步骤、转交所有权、要求所有者重新确认。删除审计和伪造运行结果不在允许范围内。

## 14. Agent 工具与查询 API

### 14.1 对话工具建议

在现有 `agent.*` 工具命名下增加：

- `agent.get_my_access_scope`
- `agent.create_automation_draft`
- `agent.preview_automation`
- `agent.confirm_automation`
- `agent.list_automations`
- `agent.get_automation`
- `agent.update_automation`
- `agent.set_automation_enabled`
- `agent.archive_automation`
- `agent.list_scheduled_triggers`
- `agent.list_automation_runs`
- `agent.get_automation_run`
- `agent.list_push_deliveries`
- `agent.get_push_delivery`
- `agent.list_automation_audit`
- `agent.simulate_automation`

同一查询工具根据服务端当前用户返回不同视图；管理员平台范围查询必须显式使用管理员工具或由服务端确认管理员身份，不能由模型自行传入管理员范围。

权限修改不注册为普通 Agent 工具。Livzon 只允许读取和解释当前有效范围，不能调用 `set_user_module_permissions` 一类操作。

### 14.2 只读查询 API

为对话中的结构化卡片、分页和刷新提供稳定 API：

- `GET /api/v1/agent/automations`
- `GET /api/v1/agent/access-scope`
- `GET /api/v1/agent/automations/{id}`
- `GET /api/v1/agent/automations/{id}/versions`
- `GET /api/v1/agent/scheduled-triggers`
- `GET /api/v1/agent/automation-runs`
- `GET /api/v1/agent/automation-runs/{id}`
- `GET /api/v1/agent/automation-runs/{id}/events`
- `GET /api/v1/agent/push-deliveries`
- `GET /api/v1/agent/automation-audit`

这些 API 不代表建设独立任务管理页面，主要服务于对话消息中的结构化展示。所有任务相关写操作继续通过 Agent 工具、Server Actions 和确认链路完成；用户授权按下一节的管理员权限管理链路执行。

### 14.3 管理员权限管理 API

用户授权是前述“所有任务操作均在对话中完成”的明确例外，由身份与权限模块提供管理员 API：

- `GET /api/v1/identity/users/{user_id}/module-permissions`
- `PUT /api/v1/identity/users/{user_id}/module-permissions`
- `GET /api/v1/identity/users/{user_id}/livzon-access-scope`
- `POST /api/v1/identity/users/{user_id}/livzon-access-scope/sync`
- `GET /api/v1/identity/users/{user_id}/permission-audit`

`PUT` 必须提交完整期望版本或 `If-Match`，防止多个管理员并发覆盖；服务端校验操作者可授权模块、权限项和数据范围，并返回新的 `grant_version` 及 Livzon 同步状态。同步接口只重建派生范围，不能新增授权。

### 14.4 分页和过滤

列表统一支持：

- `cursor` 或 `page/page_size`，首期保持项目现有风格。
- `status`、`module`、`owner`、`created_from/to`、`run_from/to`。
- `trigger_type`、`failure_code`、`channel`、`delivery_status`。
- `scope=mine/shared/platform`，其中服务端强制裁剪不允许的范围。

## 15. 前端对话体验

Livzon 继续使用全局浮动助手作为统一入口。建议在现有消息模型中增加结构化 `artifact` 元数据：

```ts
type AgentArtifact =
  | { type: "automation_list"; queryRef: string }
  | { type: "automation_detail"; automationId: string; version: number }
  | { type: "run_timeline"; runId: string }
  | { type: "push_delivery_list"; queryRef: string }
  | { type: "audit_diff"; auditId: string }
  | { type: "confirmation_preview"; confirmationId: string }
```

前端通过生成的 OpenAPI 类型消费 API，不手写后端响应类型。结构化卡片遵守现有设计系统：12px 卡片圆角、轻边框、紫色主操作、状态标签和清晰时间线；避免在聊天窗口中塞入完整后台表格。

普通用户与管理员使用同一入口，但管理员身份下可得到额外的治理查询建议和脱敏平台视图。前端不以隐藏按钮替代后端权限校验。

权限管理是对话式任务管理之外的管理功能。在管理员用户详情中提供“模块权限”区域，至少展示模块、固定权限项、数据范围、授权人、更新时间、`grant_version`、Livzon 同步状态和“重新同步”操作。权限保存使用 Server Action；保存成功不等于同步成功，界面必须分别展示授权状态和 Livzon 范围同步状态。

## 16. 安全与合规要求

- Agent、Hermes-Lite 和工作流执行器只能通过工具网关调用已注册能力。
- 用户模块授权只能由身份与权限服务写入；Livzon、Hermes-Lite、业务模块和前端缓存均不能直接修改授权事实。
- Livzon 范围快照过期、缺失或同步失败时采用 fail-closed：实时校验失败则拒绝工具调用和自动化执行。
- 所有工具输入使用 Pydantic v2 Schema；拒绝额外危险字段。
- 对话、自动化定义、日志和审计中统一执行 Secret 脱敏。
- 禁止自动化定义包含 SQL、代码、任意 URL 调用、文件路径或可执行脚本。
- 发送消息前执行收件人范围和内容敏感等级检查。
- 管理员查看他人任务和运行详情写入审计。
- 运行时业务查询使用最小数据原则；事件载荷不承载完整敏感对象。
- 高风险责任动作保持 `human_decision_required=true`、`workflow_allowed=false`。
- 自动化删除采用归档或软删除，运行和审计记录按保留策略保存。

建议默认保留期：运行摘要 365 天，步骤技术日志 90 天，推送投递 365 天，审计按公司合规策略执行且不得由普通管理员删除。具体周期由合规负责人确认。

## 17. 兼容与演进策略

### 17.1 Schema 版本

- 每个自动化定义包含 `schema_version`。
- 每个工具包含独立 `capability_version`。
- 执行器至少支持当前版本和前一个主版本。
- 不识别的新字段应按 Schema 配置拒绝或安全忽略，不得改变旧流程语义。

### 17.2 工具升级

- 兼容变更提升 minor 版本，例如新增可选输出字段。
- 破坏性变更发布新 operation 或 major 版本，旧能力进入弃用期。
- 平台定期扫描 `capability_versions`，列出受影响自动化。
- 自动迁移只允许等价、安全且可验证的字段变更；其余由所有者在对话中确认升级。

### 17.3 现有工作流迁移

1. 保留现有 `AgentWorkflow` 和相关工具，标记为 legacy-compatible。
2. 为现有顺序步骤生成 `schema_version=1.0` 的 AutomationVersion。
3. 现有 `trigger_phrases` 转为 `manual/conversation` 触发器。
4. 现有 WorkflowRun 继续可查询，不强制改写历史记录。
5. 新创建的定时和事件自动化直接使用新模型。
6. 迁移稳定后，再将旧工具内部转发到新 Service，避免前端和 Hermes-Lite 一次性切换。

## 18. 实施计划

### Phase 0：契约冻结与安全基础

目标：先建立不会随模块增长而失控的基础。

- 确认普通用户/管理员查看矩阵和敏感字段规则。
- 建立用户—模块授权事实表、授权管理 Service、管理员 API 和授权变更审计。
- 实现 Livzon 访问范围解析器、授权版本、派生快照、Outbox 同步和 fail-closed 校验。
- 定义 Automation Schema v1、受限条件 DSL、状态枚举和错误码。
- 为 `AgentToolSpec` 增加兼容元数据。
- 定义统一 `correlation_id` 和脱敏组件。
- 补齐 Agent 查询和管理员查看行为的审计要求。

验收：管理员可分配用户模块权限并看到 Livzon 同步结果；用户只能读取自己的有效范围；示例工作流可离线编译、校验和输出权限检查结果，不执行实际业务动作。

### Phase 1：持久化自动化与对话查看

目标：用户能在对话中创建、查看、修改和启停自动化基础对象。

- 新增 Automation、Version、Trigger、Run、StepRun、RunEvent 表和针对性迁移。
- 实现个人范围与管理员范围的查询 Service。
- 自动化创建和查看统一使用已同步的 Livzon 有效范围，并在授权版本变化时重新校验。
- 实现列表、详情、版本和运行时间线 API。
- 增加对话工具和结构化 artifact 渲染。
- 将现有 AgentWorkflow 以兼容方式接入新模型。

验收：普通用户只能查询本人/共享范围；管理员可查询平台元数据但业务载荷按权限脱敏。

### Phase 2：可靠定时执行

目标：通过对话创建的定时任务可以在服务重启和多实例下可靠运行。

- 实现 `AgentAutomationGenerator`。
- 持久化 `next_fire_at`、触发领取和幂等键。
- 增加并发策略、超时、重试、隔离和权限复验。
- 实现模拟运行和未来执行时间预览。

验收：重复调度实例不会重复运行；服务重启后恢复；权限撤销后自动暂停。

### Phase 3：飞书投递与闭环

目标：精准推送并可在对话中查看完整投递状态。

- 新增 PushDelivery 和模板版本记录。
- 接入本地用户到飞书身份的运行时解析。
- 实现去重、聚合、重试、失败对账和交互卡片回写。
- 增加“我的推送”和管理员投递健康查询。

验收：相同触发不重复发送；用户不能查看他人消息；管理员能定位失败但看不到无权业务内容。

### Phase 4：跨模块事件编排

目标：支持模块间数据联调和事件驱动闭环。

- 选择采购—仓储、质量—生产等一条链路作为试点。
- 发布版本化业务事件和最小事件信封。
- 增加 `event_wait`、人工待办和恢复通知。
- 建立能力弃用影响扫描。

验收：编排器不导入模块内部实现；模块能力升级有清晰兼容提示；全链路可通过一个 correlation ID 查询。

### Phase 5：运营优化

目标：形成平台中枢的主动治理能力。

- 任务健康度评分、无效任务识别、误报和失败趋势分析。
- 自动化模板和可复用子流程。
- 管理员自然语言运营报告。
- 基于历史运行的优化建议，但所有修改仍需所有者确认。

## 19. 测试计划

### 19.1 单元测试

- 自然语言计划输出的 Schema 校验。
- 用户模块授权、管理员可授权边界、授权版本并发控制和 Livzon 范围解析。
- 授权 Outbox、同步重试、快照失效和 fail-closed 行为。
- cron、时区、节假日、错过触发计算。
- 条件 DSL、字段映射和模板变量。
- 权限范围、字段脱敏、管理员治理视图。
- 幂等键、并发策略、重试和隔离状态机。
- 工具版本兼容和弃用检测。

### 19.2 集成测试

- 对话创建 → 确认 → 持久化 → 调度 → 工具执行 → 飞书投递 → 审计。
- 管理员授权 → 授权版本更新 → Livzon 范围同步 → 对话可见工具变化 → 审计。
- 普通用户访问本人、他人、共享和平台对象的允许/拒绝场景。
- 管理员有/无业务模块权限时的内容差异。
- 所有者调岗、禁用和权限撤销后的运行行为。
- 多实例调度竞争和服务重启恢复。
- 跨模块步骤失败、部分成功、重试和补偿。

### 19.3 安全测试

- Prompt 注入要求绕过权限、读取他人记录或调用未注册工具。
- Prompt 注入要求助手修改模块权限、伪造 `agent_scope_version` 或绕过同步状态。
- 在参数、模板和业务字段中注入 SQL、脚本、URL 和 Secret。
- 枚举自动化 ID、运行 ID、推送 ID 获取越权数据。
- 管理员接口越权和前端伪造 `scope=platform`。
- 审计及运行载荷中的 Secret 和敏感字段泄漏检查。

### 19.4 验收场景

至少通过以下端到端场景：

1. 管理员给用户授予仓储 `view/read/automate` 权限，Livzon 范围同步成功后，用户可查询和编排仓储只读能力。
2. 管理员无权管理质量模块时，不能给自己或他人授予质量权限。
3. 授权同步失败时，用户不能依赖旧快照新增调用；管理员可查看失败原因并重新同步。
4. 用户在对话中要求修改自身权限时被拒绝，但可查看当前有效范围和申请路径。
5. 用户创建“工作日 9 点给我发送昨日异常摘要”，确认后可查询下次执行时间。
6. 用户查看自己的任务、运行、推送和审计时间线。
7. 用户请求查看他人私人任务时被拒绝且不泄露对象是否存在。
8. 管理员查看平台失败任务，得到元数据和脱敏原因。
9. 管理员没有质量模块数据权限时，不能看到质量异常明细。
10. 用户 `module.agent.automate` 权限被撤销后，相关任务进入 `suspended_policy` 并停止执行。
11. 同一触发窗口在两个调度实例中只创建一次运行和一次推送。
12. 工具能力版本弃用后，相关自动化被识别并提示迁移。
13. 飞书接收人缺少身份映射时记录失败并给出修复建议，不误发给其他人。
14. 高风险人工决策无法进入无人值守流程。

## 20. 非功能指标

- 自动化查询接口 P95 小于 500ms，不包含外部业务数据查询。
- 到期定时任务在正常负载下 60 秒内进入运行队列。
- 调度重复触发率为 0，以幂等键和数据库唯一约束验证。
- 推送重复发送率目标为 0；无法确认时优先进入待对账状态。
- 关键状态变化审计覆盖率 100%。
- 用户模块授权变更到 Livzon 范围同步的正常链路目标 P95 小于 10 秒；同步失败必须在 60 秒内进入可见告警状态。
- 任意 Agent 请求携带过期访问范围时不得放行，过期范围误授权率为 0。
- 权限拒绝和字段脱敏测试覆盖所有查询 API 和 Agent 工具。
- 单个模块能力故障不阻塞其他独立模块的调度循环。
- 所有列表查询必须分页，所有运行步骤必须有超时上限。

## 21. 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| 大模型误解用户意图 | 结构化预览、模拟和确认；执行只读已编译定义 |
| 管理员越权看到业务内容 | 平台治理权限与业务数据权限分离，服务端字段过滤 |
| 管理员越权授予模块权限 | 校验管理员可管理范围、禁止自我提权、权限扩大确认与完整审计 |
| Livzon 权限同步延迟或失败 | 授权版本校验、Outbox 重试、派生快照可重建、过期时 fail-closed |
| 自动化因权限变化继续执行 | 每次运行前复验，失败后 `suspended_policy` |
| 多实例重复触发和重复推送 | 数据库领取、唯一幂等键、外部消息对账 |
| 跨模块强耦合 | 工具注册、`public_api.py`、稳定业务 ID 和版本化事件 |
| 工具升级破坏旧流程 | 能力版本、弃用期、影响扫描和显式迁移 |
| 日志泄漏敏感信息 | 统一脱敏、摘要化存储、查看审计和保留期 |
| 消息噪音导致用户失去信任 | 聚合、静默、摘要、隔离和任务健康度评分 |

## 22. 首期默认决策

为避免开发阶段因选择过多而停滞，本 Spec 建议采用以下默认值：

- 时区统一为 `Asia/Shanghai`，允许任务显式覆盖。
- 定时错过策略为 `run_once`，最多补执行一次。
- 并发策略为 `forbid`，上一次未结束则跳过并记录事件。
- 写操作创建和重要范围扩大必须确认。
- 只读检查步骤允许按策略重试；非幂等写步骤不自动重试。
- 连续 5 次失败自动隔离，管理员和所有者收到通知。
- 首批跨模块试点优先选择“采购到货—仓储入库”链路，其对象关系清晰、责任人明确、闭环容易验收。

## 23. 完成定义

只有同时满足以下条件，才能认为 Livzon 对话式智能运营中枢基础完成：

- 用户无需进入配置页面即可通过对话完成任务创建、查看、修改、启停和追溯。
- 管理员可在权限管理中为用户分配模块访问权限，并能查看、重试 Livzon 有效范围同步；同步范围不能超出授权事实。
- 用户在 Livzon 中只能看到和调用已同步且实时校验通过的模块能力，不能通过对话修改或提升权限。
- 用户与管理员查看范围由服务端固定规则区分，且管理员业务内容仍受模块数据权限约束。
- 独立模块无需耦合其他模块即可接入；跨模块流程只通过注册能力、公开契约和事件协作。
- 定时任务在重启、多实例和失败重试场景下保持幂等和可恢复。
- 自动化、运行、步骤、工具调用、推送和审计可以形成完整时间线。
- 新模块和新工具能够通过版本化能力清单渐进接入，并能识别对现有自动化的兼容影响。
