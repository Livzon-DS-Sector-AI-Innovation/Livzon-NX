# Dazah 架构优化分阶段实施方案

保留模块化单体和业务数据所有权。第一阶段把质量飞书只读镜像的每日同步移到独立后台进程（worker），用一次可回切的迁移验证发布隔离、数据一致性和故障恢复。第二阶段收紧跨模块调用，第三阶段随业务迭代提取共用机制。独立部署业务微服务的决策留到有运行数据时再做。

## 第一阶段　盘点后台任务并试点独立运行

[后台任务逐项盘点与试点运行手册](background-task-inventory-and-worker-runbook.md)记录注册基线、开发环境切换和回滚步骤。

### 现有任务分布与盘点交付物

以下是从 [API 生命周期](../dazah-backend/app/main.py) 可定位的入口。实施时由后端维护者按实际注册项逐项登记，部署维护者补充启用条件、副本数与最近运行记录。代码中存在入口只说明具备该能力，启用状态以目标环境为准。

| 入口或任务族 | 已识别的工作 | 盘点重点 |
| --- | --- | --- |
| SchedulerRegistry 的生成器 | 质量与行政飞书读取、设备巡检及维修镜像、生产计划同步、仓储同步与分析、Agent 推送、人事提醒、能源通知等 | 区分外部读取、本地写入和外部投递；分别记录增量、全量和手工补跑入口 |
| SchedulerRegistry 的静态任务 | 用户操作记录保留处理、按条件注册的仓储同步与全量同步 | 数据清理范围、开关、与其他仓储任务的重叠 |
| 独立 asyncio 循环 | HR 成员同步、安全定时任务和镜像同步、权限范围同步引擎 | 权限数据生效时点、停止顺序、积压恢复 |
| 飞书连接和轮询 | 仓储、生产、设备、安全、HR 的连接启动路径，以及签署中继轮询 | 连接所有者、断线重连、重复事件和外部副作用 |
| 生产模块自有调度 | MC、FA、DR 同步启动与停止函数 | 内部时钟、持久化进度、与统一调度器共享的资源 |

盘点完成条件：将每个注册、启动和停止入口配对，沿间接启动函数继续追踪，并对照部署入口补查 API 之外的常驻进程。每项登记业务所有者、触发条件与时区、读写目标、超时与重试、互斥键及有效期、最近成功的判据、手工入口和恢复方式。未知项明确责任人；试点项的未知项须在切换前关闭。保留 API 原模式的注册清单，作为迁移后的逐项比对基线。

### 试点选择与改动范围

选定任务名为 `quality.feishu_read_daily_sync`。质量模块拥有镜像数据，飞书是读取源，本地写入包括镜像、同步状态与运行记录。结果可用固定飞书样本重放并核对，且已有按模块和资源 ID 加锁的同步方法，手工同步也调用该方法。相比通知和签署，该任务的验收无需模拟撤回已发送消息或撤销签署。[任务定义](../dazah-backend/app/platform/integrations/feishu/read_scheduler.py) · [镜像同步](../dazah-backend/app/platform/integrations/feishu/read_mirror.py) · [手工同步入口](../dazah-backend/app/modules/quality/api/read_mirror.py)

1. **保留现有业务语义。** 生成器每 15 分钟检查一次，上海时间 02:00 前跳过，按 UTC 日期和最近完整同步时间判断到期。这两个时间口径应分别测试。配置缺失时执行函数可直接返回，成功判据须取自资源完成时间及运行记录。
2. **分离注册和启动。** 复用现有后端镜像、数据库、Redis、配置加载和 SchedulerEngine。新增只注册该生成器的 worker 入口，支持维护模式、优雅退出和资源释放。API 在原模式继续注册全部现有任务，在 worker 模式仅移出该生成器。手工同步继续经原 API 鉴权。开发 Compose 先接入；交付 Compose 和发布就绪检查随受控切换适配。若引入运行模式环境变量，同步根目录两份环境示例，默认沿用 API 模式。
3. **补足跨进程执行保护。** 引擎的上次运行时间保存在进程内。资源锁保护并发写，但两个进程可能先后执行同一份过期候选清单。定时路径应在获得资源锁后重新读取完成时间并判断是否仍到期，手工强制刷新保留原语义。验证 30 分钟锁有效期与执行超时相撞时的行为，确保旧持有者失去锁后不能覆盖新结果。验证进程被强杀后已提交的 running 记录能被识别并收敛。[调度引擎](../dazah-backend/app/platform/scheduler/engine.py)
4. **建立切换基线。** 记录每资源的最近成功时间、运行状态、任务耗时、失败原因和锁冲突，日志仅含脱敏标识。先部署支持两种模式的版本，保持原模式运行；待旧实例全部具备切换能力，停止 API 对该任务的新调度，确认在途任务结束，再启用 worker。其他生成器和监听器继续按原入口运行。

### 验收标准

数据库用例使用专用测试库，飞书响应使用固定样本。容器演练使用开发镜像。后端与部署维护者共同保存以下实际结果，再决定是否推广。

| 场景 | 通过条件 |
| --- | --- |
| 注册及权限 | 原、新模式任务清单对比仅该任务移动；worker 仅注册一项。未授权用户手工同步被拒绝，授权调用沿用原有资源锁。维护模式下后台执行遵守现有维护约束。 |
| 结果与时间边界 | 同一基线、同一分页样本下，两种模式的业务记录键、字段和删除标记一致。覆盖上海时间 02:00 和 UTC 换日边界；缺失配置和上游失败均不推进最近成功时间。 |
| 并发与重放 | 两个 worker 同时发现同一资源，或其中一个延迟到首次完成后才执行，同一到期窗口仅有一次有效定时完成。手工与定时并发时不交错写入；锁失效后旧执行者不能提交过期结果。 |
| 故障与恢复 | 模拟飞书分页失败、Redis 不可用及进程在记录 running 后退出。上一次完整镜像仍可读，失败可定位；依赖恢复且遗留锁到期后，在下一次符合条件的扫描中完成补跑，遗留运行有可解释的终态。 |
| 发布与切换 | 在同步中单独重启 API，worker 能完成本轮；停止 worker 后 API 健康且已有镜像可读。完成一次反向切换演练，并观察至少一个真实调度窗口，核对到期资源及其他任务的运行清单。 |

### 回滚方式

出现重复有效完成、镜像差异、过期写入、连续错过应执行窗口或 API 健康异常时，由部署维护者发起回切，质量模块维护者核对数据。

1. 停止 worker 接收新任务，等待在途执行结束。异常退出时核对资源锁持有情况、到期时间和运行记录，待锁自然释放或到期后接管。
2. 确认 worker 实例均已退出，再恢复 API 注册模式并滚动重启。核对健康检查、注册清单和实际执行者，防止两个入口同时调度。
3. 按受影响资源对账最近完整同步时间、镜像内容和运行记录。遗漏或异常资源经已有授权入口重新同步；保留原运行记录供审计。若源数据已变化且需恢复历史值，转入质量模块的数据恢复流程。
4. 以下一轮到期资源成功、页面可读、其他任务清单与基线一致作为回滚完成条件。试点按兼容现有 schema 设计；若实现发现需新增持久状态，先补充迁移兼容和回切方案。

## 第二阶段　收紧跨模块依赖

按记录所有者逐条迁移，每条独立交付。质量读取 HR 信息时由 HR 公开查询提供最小字段，比较迁移前后的数据范围和历史员工结果；能源 Wiki 对仓储飞书客户端的依赖迁到对应平台协议能力，核对凭据归属与错误行为；Agent 生成采购合同时改走采购公开入口，比较页面与 Agent 的权限、合同结果及来源审计。以受影响调用方的契约测试和新增私有导入检查作为退出条件。[业务归属规范](business-module-boundaries.md)

## 第三阶段　按实际调用方提取共用机制

先用采购物料选项与质量验证列表检验读取缓存的共用边界，覆盖权限隔离、缓存失效和 Redis 降级。再按真实重复点复用飞书协议与读取镜像能力，字段映射、审批和业务状态继续由所属模块解释。前端接口传输类型优先使用生成契约，页面组合与展示转换由调用方负责。每次抽取至少列出两个实际调用方，并通过各自的行为回归测试。

## 后续服务拆分的决策条件

试点稳定后按任务族评估推广。对有外部副作用的任务，先证明去重、补偿与审计可用。定期比较 API P95 延迟、任务积压、镜像新鲜度、发布中断和故障影响范围。若独立后台进程仍无法满足明确的容量、隔离或发布目标，再由模块所有者提出独立服务方案，列出数据所有权、跨服务事务、运维成本和回退路径。Hermes 继续通过既有工具网关执行业务动作。
